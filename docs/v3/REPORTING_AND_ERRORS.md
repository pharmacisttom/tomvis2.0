# Reporting and Framework error feedback

Implemented: Python report engine with registered permission-scoped dataset adapters, bounded filtering, column allowlists, grouping/count summaries, tenant isolation, generation audit, React report studio, CSV export with formula-prefix protection and dedicated A4 landscape print styles. Browser print supports choosing Save as PDF where the browser supplies it; this is not a server PDF renderer.

Available datasets: Feedback and Users. The engine is domain-neutral; accounting and HR need separately validated adapters, actual schema, decimal monetary aggregation, reconciliation/payroll rules and product permissions. They are not simulated as complete modules. Current output caps at 1000 returned records and clearly reports truncation; grouping covers returned records only. XLSX, scheduled jobs, AI/natural-language reports, server-rendered PDF, logos, page numbering, approval/signature templates and financial totals remain pending. Report execution never accepts raw SQL.

Unexpected Python API exceptions produce safe generic public errors with Request ID. Authenticated incident metadata is stored transactionally in a tenant-owned `error_reports` table (migration 3), grouped by fingerprint, category, component and Framework version. Exception messages, payloads, local variables, credentials and full file paths are excluded. Failed business/audit transactions roll back before incident recording. If the database is unavailable, local incident storage may also fail; resilient external observability is pending.

Next page/global error boundaries display safe retry screens and submit only fixed `UI_RENDER_ERROR`/component metadata for authenticated users. The incident endpoint rejects additional fields, requires CSRF Origin and session, and deduplicates incidents. It never receives React exception text/stack or user payloads. Anonymous UI faults are not persisted as tenant incidents.

The System errors page is available to users with `audit.view` and cannot read another tenant's incidents. A central developer collector, per-customer opt-in, transport credentials, retention/redaction, grouping across installations and reviewed release delivery remain pending. No customer errors are transmitted externally. Fixes to shared packages can be delivered through versioned Framework releases; tenant deployments must still update through a controlled rollout. This is not automatic self-modifying code or a guarantee that all module errors have a common fix.
